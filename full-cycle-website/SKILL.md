# Сайт под ключ: от идеи до продакшена

Цель: рабочий сайт на домене по HTTPS в Docker, с SEO-базой, документацией API, git-историей, инструкцией по ручной установке и скриптом обновления, который запускается одной командой `curl`. Сайт должен уживаться на сервере с уже существующими сайтами и прокси. Готово, только когда пройден чек-лист приёмки в конце.

## 0. Бриф (спросить один раз, остальное решать самому)
Узнать у пользователя только то, чего нельзя вывести самому:
- назначение сайта, страницы, языки, целевая аудитория и регион;
- домен (регистрирует пользователь сам, например на reg.ru) и нужен ли `www`;
- сервер: IP, SSH-пользователь, ОС; новый он или на нём уже живут другие сайты. Секреты никогда не просить в чат, только через защищённый ввод (переменные окружения);
- репозиторий (GitHub/GitLab/другой), публичный или приватный, и куда слать уведомления;
- нужны ли формы, CMS, аналитика (Яндекс Метрика / GA), бэкенд, API, БД.
Всё остальное (стек, структура, конфиги) выбрать самостоятельно и кратко зафиксировать в `docs/DECISIONS.md`.

## 1. Дизайн: DESIGN.md
- Дизайн-система создаётся отдельными скиллами пользователя и лежит в `DESIGN.md` в корне репозитория (или указанном пользователем месте).
- Если `DESIGN.md` есть: прочитать его до начала вёрстки и строго следовать ему (цвета, типографика, сетка, отступы, компоненты, тон). Не переписывать и не дополнять его по своей инициативе; найденные пробелы и противоречия перечислить пользователю.
- Если `DESIGN.md` нет: спросить, будет ли он; если пользователь просит не ждать, сделать нейтральный аккуратный дизайн и отметить это в отчёте.
- Дизайн-токены из `DESIGN.md` вынести в CSS-переменные / конфиг темы, а не хардкодить.

## 2. Стек и Docker (обязательно)
- Контентный/лендинг: статический генератор (Astro, Next.js static export, Hugo), отдаваемый лёгким контейнером (nginx:alpine / caddy:alpine внутри контейнера приложения).
- Динамика: Next.js/Nuxt/Django/Laravel/FastAPI и т.п.
- Всё приложение (сайт, бэкенд, БД, воркеры) работает в Docker через `docker-compose.yml` (и `docker-compose.prod.yml` при необходимости). Многоэтапный `Dockerfile`, непривилегированный пользователь в контейнере, `HEALTHCHECK`, `restart: unless-stopped`, ограничения логов (`max-size`).
- Изоляция от других сайтов на сервере:
  - уникальное имя проекта Compose (`name: <project>` / `COMPOSE_PROJECT_NAME`), все контейнеры, сети и тома с префиксом проекта;
  - БД и внутренние сервисы без публикации портов наружу, только во внутренней сети проекта;
  - веб-контейнер публикуется только на `127.0.0.1:<APP_PORT>`, никогда на `0.0.0.0` и никогда на 80/443; `APP_PORT` задаётся в `.env`.
- Образы помечать тегом версии (`<project>:v1.2.3` и `:sha-<commit>`), чтобы откат был возможен.

## 3. Репозиторий и версионирование
- `git init`, `.gitignore`, `.dockerignore`, `.editorconfig`, `README.md` (как запустить локально, ссылка на инструкцию установки, команда обновления), `.env.example` без реальных секретов.
- Ветки: `main` = продакшен, работа в feature-ветках, слияние через PR.
- Conventional Commits, семантические версии (`v1.0.0`), `CHANGELOG.md`; теги на релизы.
- Линтер, форматтер, pre-commit хуки; тесты хотя бы на сборку, ключевые страницы и эндпоинты API.

## 4. Разработка
- Адаптивная вёрстка по `DESIGN.md`, доступность (alt, контраст, семантичные теги, порядок заголовков).
- Производительность: оптимизация изображений (WebP/AVIF, `srcset`, lazy-load), минимум JS, кэширование статики, шрифты с `font-display: swap`.
- Страницы 404/500, favicon и `site.webmanifest`.
- Формы: валидация, защита от спама (honeypot/капча), отправка на почту/в Telegram через переменные окружения.
- Эндпоинт `/health` (или `/api/health`) для проверок обновления и мониторинга.
- Юридическое: политика конфиденциальности и согласие на cookies при наличии аналитики (для РФ учесть 152-ФЗ).

## 5. Документация API
Если у сайта есть API (свой бэкенд, эндпоинты форм, вебхуки), документация обязательна и живёт в репозитории:
- Спецификация OpenAPI 3 в `docs/api/openapi.yaml`, генерируемая из кода, где фреймворк умеет (FastAPI, NestJS, drf-spectacular и т.п.), иначе написанная вручную и проверенная валидатором.
- `docs/API.md`: базовый URL, аутентификация, форматы ошибок, лимиты, версионирование API (`/api/v1`), и для каждого эндпоинта: метод, путь, параметры, тело запроса, ответы с кодами и примеры `curl`.
- Интерактивная документация (Swagger UI / Redoc / Scalar) по адресу `/api/docs`; в продакшене закрыть её basic auth или по IP, если API не публичный.
- CI проверяет, что спецификация валидна и совпадает с кодом.
- При изменении API обновлять спецификацию, `docs/API.md` и `CHANGELOG.md` в том же PR.

## 6. SEO
- `robots.txt` (со ссылкой на sitemap; закрыть `/api/`, админку и служебные пути; на staging закрыть индексацию полностью).
- `sitemap.xml` генерируется автоматически при сборке.
- Уникальные `<title>` и `meta description` на каждой странице, `canonical`, `hreflang` для мультиязычности, `lang` у `<html>`.
- Open Graph и Twitter Card, структурированные данные JSON-LD (Organization, WebSite, BreadcrumbList, Product/Article по ситуации).
- Человекопонятные URL, единый вариант домена (301 с www/без www и с http на https), без цепочек редиректов.
- Подготовить инструкцию для пользователя: подтвердить сайт в Яндекс Вебмастере и Google Search Console, отправить sitemap.

## 7. Аудит сервера перед установкой (только чтение)
Перед тем как писать инструкцию, если есть SSH-доступ, собрать картину сервера только читающими командами; если доступа нет, включить эти команды первым шагом инструкции, чтобы пользователь прислал вывод:
- ОС и ресурсы: `cat /etc/os-release`, `free -h`, `df -h`.
- Занятые порты и кто их держит: `ss -ltnp`.
- Прокси на хосте: `systemctl is-active nginx caddy apache2 haproxy traefik`, `nginx -T` (список `server_name`), `caddy list-modules`/содержимое `/etc/caddy/Caddyfile` и подключаемых файлов.
- Прокси в Docker: `docker ps --format '{{.Names}} {{.Image}} {{.Ports}}'` (nginx-proxy, Traefik, Caddy, NPM на 80/443).
- Существующие Compose-проекты, сети и тома: `docker compose ls`, `docker network ls`, `docker volume ls`.
- Уже выпущенные сертификаты и кто их продлевает (certbot timers, Caddy storage).
- Firewall: `ufw status` / `nft list ruleset`.
По итогам выбрать один из сценариев:
- **A. Чистый сервер.** На 80/443 никого нет: поставить Caddy (по умолчанию) или NGINX как общий reverse proxy для всех будущих сайтов, чтобы следующие сайты подключались в него же.
- **B. На хосте уже есть NGINX.** Не ставить второй прокси. Добавить только свой файл `/etc/nginx/sites-available/<domain>.conf` (или `conf.d/<domain>.conf`) с `proxy_pass http://127.0.0.1:<APP_PORT>`, symlink в `sites-enabled`, сертификат через `certbot --nginx -d <domain>` (или webroot), который трогает только свой server-блок.
- **C. На хосте уже есть Caddy.** Добавить отдельный файл сайта (`/etc/caddy/sites/<domain>.caddy`), подключённый через `import`, и если `import` ещё нет, добавить одну строку `import sites/*` в основной Caddyfile, сохранив резервную копию.
- **D. Прокси работает в Docker (Traefik, nginx-proxy, Caddy-docker-proxy, NPM).** Подключить контейнер к его сети и описать сайт метками/переменными (`VIRTUAL_HOST`, labels Traefik) вместо публикации порта; не трогать конфигурацию самого прокси.
- **E. Неизвестный или нестандартный прокси, или конфликт, который нельзя решить безопасно.** Остановиться и описать пользователю ситуацию и варианты.
Общие правила конфликтов:
- Никогда не занимать 80/443 контейнером проекта, не останавливать, не перезапускать и не переписывать чужие сайты, контейнеры, сертификаты и конфиги.
- `APP_PORT` выбирать свободным (`ss -ltn` + проверка `docker ps`), из диапазона, например 8100–8999, и записывать в `.env` и `docs/DECISIONS.md`.
- Перед добавлением домена убедиться, что такой `server_name`/адрес ещё не обслуживается другим конфигом.
- Любое изменение прокси: сначала резервная копия файла, затем проверка (`nginx -t` / `caddy validate --config ...`), затем только `reload`, не `restart`; при ошибке проверки откатить свой файл и не перезагружать.
- Не менять глобальные настройки сервера (SSH, firewall, Docker daemon), если сервер уже настроен и обслуживает другие сайты; рекомендации по харденингу дать отдельным необязательным разделом.

## 8. Ручная установка: `docs/INSTALL.md`
Установку пользователь выполняет вручную по пошаговой инструкции, которую готовит агент под выбранный сценарий (A–E). Не делать установочный скрипт `curl | bash`. Инструкция должна:
- для каждого шага давать точные команды для копирования, объяснение в одну строку и команду проверки результата;
- начинаться с аудита (раздел 7) и явно разветвляться по сценарию;
- включать: установку Docker и Compose, если их нет (официальный репозиторий Docker); создание пользователя деплоя и каталога `/opt/<project>` (или `/srv/<project>`); настройку deploy key (раздел 9); клонирование; заполнение `.env` из `.env.example` с выбором свободного `APP_PORT`; первый `docker compose up -d --build` и проверку `curl -fsS http://127.0.0.1:<APP_PORT>/health`; подключение к прокси по сценарию; DNS (раздел 10) и выпуск SSL; настройку бэкапов; проверку сайта по HTTPS;
- для чистого сервера (сценарий A) добавлять базовый харденинг: пользователь с sudo, вход только по ключу, ufw (22, 80, 443), fail2ban, автообновления безопасности, swap при малой памяти;
- заканчиваться разделом «Что делать, если…» с типовыми ошибками (порт занят, `nginx -t` падает, сертификат не выпускается из-за DNS, контейнер не здоров) и как откатить свои изменения, не задев другие сайты.
Конфиги для прокси положить в репозиторий как шаблоны: `deploy/nginx/site.conf.template`, `deploy/caddy/site.caddy.template`, `deploy/traefik/labels.example`.

## 9. Доступ сервера к репозиторию: Deploy key (обязательно)
Сервер забирает код только через отдельный deploy key, привязанный к одному репозиторию, а не через личные ключи или токены пользователя.
- На сервере под пользователем деплоя: `ssh-keygen -t ed25519 -C "deploy@<домен>" -f ~/.ssh/<repo>_deploy -N ""`.
- Прописать в `~/.ssh/config` алиас хоста (`Host github-<repo>`, `HostName github.com`, `IdentityFile ~/.ssh/<repo>_deploy`, `IdentitiesOnly yes`), чтобы на сервере могли жить несколько сайтов со своими ключами; отпечаток хоста добавить в `known_hosts` через `ssh-keyscan`.
- Публичную часть добавить в репозиторий как Deploy key только на чтение (GitHub: Settings, Deploy keys, Allow write access выключен; GitLab: Settings, Repository, Deploy keys). Если у агента есть доступ к API репозитория с правами администратора, добавить ключ через API (GitHub: `POST /repos/{owner}/{repo}/keys` с `read_only: true`) после согласия пользователя; иначе в инструкции указать точное место, куда вставить ключ.
- Проверить: `ssh -T git@github-<repo>` и `git ls-remote git@github-<repo>:<owner>/<repo>.git`.
- Приватный ключ никогда не покидает сервер и не попадает в git, чат или логи CI.
- Для запуска обновления из CI использовать отдельный ключ (в секретах CI, публичная часть в `authorized_keys` пользователя деплоя, по возможности с ограничением `command=` на скрипт обновления); не путать его с deploy key.

## 10. Домен и DNS
Домен регистрирует пользователь. Выдать ему точную инструкцию для его регистратора:
- запись `A` для `@` на IP сервера (и `AAAA`, если есть IPv6);
- `A` или `CNAME` для `www`;
- при почте на домене: MX, SPF, DKIM, DMARC.
Проверить распространение через `dig`/`nslookup` и только потом выпускать SSL-сертификат.

## 11. Скрипт обновления через curl: `deploy/update.sh`
Единственный автоматизированный скрипт для сервера: обновляет уже установленный сайт. Запуск на сервере под пользователем деплоя:
```
curl -fsSL https://raw.githubusercontent.com/<owner>/<repo>/main/deploy/update.sh | bash -s -- --dir /opt/<project> --ref v1.2.3
```
Для приватного репозитория raw-ссылка без авторизации недоступна; тогда команда в README использует локальную копию из клона (`bash /opt/<project>/deploy/update.sh --ref v1.2.3`) или скачивание релиз-ассета; выбрать вариант и описать его в README и `docs/INSTALL.md`.
Требования:
- `#!/usr/bin/env bash`, `set -euo pipefail`, понятные сообщения о каждом шаге, лог в каталоге проекта (`/opt/<project>/logs/update.log`).
- Параметры: `--dir` (каталог установки), `--ref` (ветка, тег или коммит, по умолчанию последний тег или `main`), `--dry-run`, `--rollback`, `--yes`.
- Предпроверки: каталог существует и это git-клон нужного репозитория, `.env` на месте, Docker доступен, свободного места на диске достаточно; иначе остановиться без изменений и подсказать, что установка делается по `docs/INSTALL.md`.
- Блокировка через `flock`, чтобы два обновления не шли одновременно.
- Шаги: запомнить текущий коммит и теги образов; `git fetch` через deploy key и `checkout` нужного `--ref`; сравнить `.env.example` с `.env` и предупредить о новых переменных (не перезаписывать `.env`); бэкап БД перед миграциями; `docker compose pull`/`build`; `docker compose up -d` только для своего проекта (`-p <project>`); миграции; ожидание `/health` на `127.0.0.1:<APP_PORT>` с таймаутом.
- Если проверка не прошла: автоматический откат на предыдущий коммит и образы, повторная проверка, ненулевой код выхода и понятное сообщение.
- Если в обновлении изменился шаблон прокси: не применять молча, а вывести diff и команду для ручного применения (с `nginx -t`/`caddy validate` и `reload`), потому что прокси общий.
- Никогда не трогать чужие Compose-проекты, контейнеры, сети, тома и конфиги прокси; чистить только старые образы своего проекта, оставляя последние N для отката.
- В конце: версия до и после, статус `/health`, URL сайта, как откатиться (`--rollback`).
- Скрипт проходит `shellcheck`; его проверка на тестовом окружении (контейнер или ВМ с той же ОС) обязательна.

## 12. CI/CD
- CI на каждый PR: установка зависимостей, линт, тесты, сборка Docker-образа, проверка спецификации API, `shellcheck` для `deploy/*.sh`.
- Релиз: тег `vX.Y.Z` собирает и пушит образ в registry (если используется) и создаёт GitHub Release с CHANGELOG.
- CD (по желанию пользователя): после релиза CI по SSH вызывает на сервере `deploy/update.sh --ref <тег> --yes` и падает, если скрипт вернул ошибку. Без согласия пользователя автодеплой не включать, обновление тогда запускается командой `curl` вручную.
- По желанию: staging-окружение на поддомене с закрытой индексацией.
- Секреты только в секретах CI и `.env` на сервере, никогда в git.

## 13. Эксплуатация
- Бэкапы: БД и загружаемые файлы по расписанию (cron/systemd timer пользователя деплоя), хранение вне сервера, проверка восстановления.
- Мониторинг доступности (uptime-чек по `/health`), ограничения логов Docker, оповещение об истечении SSL.
- Аналитика (Метрика/GA) при согласии пользователя.

## 14. Чек-лист приёмки (проверить самому, не на словах)
- [ ] Вёрстка соответствует `DESIGN.md` (если он есть), отклонения перечислены.
- [ ] Всё работает в Docker; веб-контейнер слушает только `127.0.0.1:<APP_PORT>`, порты 80/443 проектом не заняты.
- [ ] Другие сайты и контейнеры на сервере работают как до установки; конфиг прокси проходит `nginx -t` / `caddy validate`.
- [ ] Сайт открывается по `https://домен` и `https://www.домен` с одним каноничным вариантом, http редиректит на https.
- [ ] Валидный SSL, автопродление настроено.
- [ ] `robots.txt` и `sitemap.xml` доступны и корректны; meta, OG, JSON-LD на месте.
- [ ] Lighthouse: Performance, SEO, Accessibility, Best Practices не ниже 90 (или объяснить, почему нет).
- [ ] 404 работает, битых ссылок нет.
- [ ] Документация API: `openapi.yaml` валиден, `docs/API.md` актуален, `/api/docs` открывается, примеры `curl` работают.
- [ ] Сервер забирает код через deploy key только на чтение; личных ключей и токенов на сервере нет.
- [ ] `docs/INSTALL.md` пройден по шагам на тестовом окружении для нужного сценария.
- [ ] Команда обновления `curl ... update.sh` обновляет сайт, а при сломанном релизе сама откатывает его.
- [ ] Бэкап создаётся и восстанавливается.
- [ ] В репозитории есть README (с командой обновления), `docs/INSTALL.md`, DECISIONS, CHANGELOG, `docs/API.md`, `deploy/`; секретов в git нет.

## 15. Отчёт пользователю
Коротко: ссылки на сайт, репозиторий и документацию API; выбранный сценарий сервера и `APP_PORT`; ссылка на `docs/INSTALL.md`; команда обновления `curl` целиком; что пользователю осталось сделать руками (шаги установки, DNS у регистратора, deploy key, если агент не мог добавить сам, подтверждение в Вебмастере/Search Console).

## Правила
- Действия, которые меняют прод или чужие аккаунты (DNS, deploy key через API, конфиг общего прокси, удаление данных, оплата), согласовывать с пользователем.
- На общем сервере менять только то, что принадлежит проекту; всё общее (прокси, firewall, SSH) только с резервной копией, проверкой и согласием.
